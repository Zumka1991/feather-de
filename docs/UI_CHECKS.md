# Иконки Dock точного размера, 2026-10-23 (Claude)

**Причина.** FEATHER_PROFILE_UI с новым счётчиком `icon` показал: перерисовка Dock в 4K ×2
стоила 16,6–28,1 мс CPU, из них ~80 % — масштабирование иконок 192 px → 100 px фильтром
Bicubic tiny-skia на главном потоке. Dock перерисовывается при каждом движении курсора
над ним (увеличение включено по умолчанию), при запуске/закрытии окон и смене размера.

**Изменение.** Если физический размер иконки целый (×1, ×1,5, ×2, ×3 для Dock в покое,
Spotlight, переключателя, перетаскивания), worker растеризует её ровно этого размера,
главный поток копирует пиксели без фильтра (позиция округляется до физического пикселя).
Увеличенные при наведении иконки Dock всегда идут прежним путём из корзины 64/192/320,
чтобы движение курсора не порождало задания для промежуточных размеров. Пока нужный
размер не готов, масштабируется любой другой размер той же иконки из кэша, а не рисуется
заглушка; ставится только одно задание. Превью 64 px после вытеснения по-прежнему
масштабируется, не копируется. Новых потоков, таймеров и опроса нет.

**Проверка.** Release без предупреждений, `dbus-run-session -- cargo test -- --include-ignored`
— 32 passed (новый тест: точный размер копируется без масштабирования и сдвига, до его
прихода — масштабирование кэша без второго задания, превью вытеснения, размер для другой
поверхности, увеличенная иконка не ставит задание). Снимки самого композитора ×2 до/после:
положение и размер иконок совпадают, отличаются ~0,1 % пикселей на краях (растеризация
вместо ресемплинга); ×1,25 не изменился (дробный размер идёт старым путём).

Активный Hyprland (tty2 в начале и конце каждого прогона), вложенный 1920×1080 ×2,
CPU потока по FEATHER_PROFILE_UI:

| Перерисовка Dock | До | После |
|---|---:|---:|
| С готовыми иконками, 4K | 16,6 / 18,9 / 25,4 / 27,2 / 28,1 мс | 3,1–3,5 мс |
| Из них иконки | ~14–24 мс | ~1,3–1,4 мс |
| Переходный кадр после смены размера окна | 28,1 мс | 9,1 мс |

Обычный FEATHER_PROFILE: ~60 Гц, «следующие» CPU первой анимации 1,09–1,32 → 0,53–0,55 мс,
RssAnon после Launchpad 34,0–35,0 МиБ, пик проб 100 мс ~53 МиБ у обеих сборок.

**Наблюдения, не принятые как результат.** Wall-время первых кадров меню/CC/Spotlight
между прогонами одной и той же сборки различается в 2–4 раза (например, меню 1,3 и 7,8 мс
CPU): первые кадры приходятся на выход CPU из простоя и зависят от нагрузки хоста.
Пользователь работал в Hyprland во время замеров: в одном прогоне простой дал 6 (до) и 2
(после) тиков при 10–151 кадрах/с без изменений — это события хоста; в остальных 0–1.
Пики «сцена+GL» 2–9 мс на первых кадрах без GPU-таймеров не разложены: overlay уже
ограничен панелями, гипотеза о загрузке 4K-текстуры для меню не подтвердилась.
Gemini 4 Argon Medium сделал ревью по тексту изменения: подтверждены и исправлены
промежуточные размеры при увеличении и заглушка вместо другого кэшированного размера;
гонка epoch не подтвердилась (`invalidate_all` очищает и `pending`). Остальное — прежнее
поведение: ×1,25 (62,5 px) идёт старым путём, превью после вытеснения масштабируется,
любая новая иконка помечает все поверхности грязными.

Артефакты: scratchpad сессии Claude (`before/`, `final*/`, `uicmp*/`, `gemini1/`).

# Первые CPU-кадры панелей, 2026-10-23

Задача: сократить синхронную подготовку меню и Control Center, сохранив стекло, сглаживание,
дробные масштабы и отсутствие фоновой работы в простое.

## Причина и изменение

Добавлен опциональный `FEATHER_PROFILE_UI=1`: отдельные стадии CPU-кадра и затраты
`fill` / `stroke` / `frosted` / `text` / `metrics`. Без этого флага диагностика не читает часы и ничего не
печатает. Наблюдение за CPU sampling через perf недоступно с текущими правами;
настройки ядра не менялись, использованы замеры стадий собственного тестового процесса.
Счётчики thread-local: работа растеризатора в worker не прибавляется к главному потоку.
В подробном выводе отдельно показаны wall и CPU по `CLOCK_THREAD_CPUTIME_ID`, чтобы
время работы не смешивалось с вытеснением потока планировщиком. Обычный FEATHER_PROFILE
сохраняет прежние wall-замеры — они не подменены новым счётчиком. Диагностический вывод
и вызовы часов не входят в основной сравнительный прогон.

Диагностический dev-прогон до оптимизации: overlay меню ~14 мс, из них ~12 мс —
заливки, стекло и обводки; Control Center ~39 мс, из них ~35 мс те же примитивы.
Это поиск причины, не release-результат: сравнивать эти цифры с финальным release нельзя.

`ui_raster.rs` оставляет tiny-skia построение той же маски AA, но вместо общего RGBA
shader pipeline применяет целочисленный premultiplied source-over. Скрещивания каналов
при умножении нет, округление — деление на 255. Маска ограничена физическим пересечением
фигуры и буфера, а не полным экраном. Обводки пока рисуются прежним путём tiny-skia.

Внутри полностью покрытых участков x86_64 используется SSE2 (обязательный для этой ABI),
четыре пикселя за шаг. Загрузки/записи unaligned, только целые блоки внутри slices;
хвост и частичное покрытие — скалярные. На других архитектурах остаётся скалярный путь.
Выделяется только первая непрерывная полоса coverage=255: отверстия/остальные полосы
обрабатываются маской, предположения о выпуклости будущих фигур нет. Новых требований
к CPU (AVX/SSE4 и т. п.) нет. Попиксельные тесты проходят и через векторные участки.

Обрезка подписи с многоточием теперь идёт линейно: накопленный advance и kerning вместо
повторного измерения каждого префикса. Индекс глифа хранится с его маской; запрос kerning
читает только нужную таблицу по проверенному диапазону mmap, не разбирает заново весь TTC.
Шрифт и таблицы остаются immutable/общими, новые словари или блокировки не добавлены.

Размытый фон по-прежнему билинейный: координаты физических центров пикселей, логический
origin и масштаб учитываются как раньше. Две горизонтально интерполированные строки
переиспользуются для соседних строк назначения. Общая формула bilinear с 8-битными весами
поддерживает Pad и premultiplied alpha, включая сглаженные края панели. Полноразмерная
копия обоев не добавляется; scratch освобождается после рисования. Damage, hit testing
и GPU-анимации сохраняют прежнее поведение.

В стеклянной панели фон и тонировка объединены в один проход/одну маску. Полностью
покрытые непрозрачные пиксели смешиваются сразу, а сглаженные края сохраняют два слоя
coverage как прежде; прозрачный источник не заменяет этот порядок. Новый zeroed-буфер
overlay не очищается повторно. При повторном использовании буфера очистка прежнего и
нового damage сохранена — старый текст/подсветка не остаются.

Статическая основа Control Center (стекло, обводка и поверхности карточек) готовится
на существующем raster worker после получения обоев. Главный поток только ставит
ограниченный запрос и копирует готовые строки; до получения результата доступен обычный
путь рисования. Текст, кнопки и ползунки остаются динамическими. Хранятся две основы
только для текущей темы/геометрии: без toast и с ним. При дробном масштабе разные origin
оверлея меняют фазу AA, поэтому один вариант нельзя без потерь подставить вместо другого.
Буферы ограничены прямоугольником панели/уведомления, не всем экраном. Worker хранит
низкое разрешение размытого фона, не полноразмерные обои. Смена конфигурации сбрасывает
основы и epoch отбрасывает устаревшие результаты. Фоновых таймеров/опроса не добавлено.

## Проверка

22 теста, включая попиксельные сравнения с прежним RGBA pipeline:

- Заливки при ×1/1,25/1,5/2/3, обычных/дробных/обрезанных краях, радиусе 0 и разных alpha.
- Стекло при ×1/1,25/1,5/2, дробном/отрицательном origin, Pad на краях текстуры и полупрозрачном
  источнике. Допуск — максимум 2 уровня канала из 255, без допуска на смещение геометрии.
- Линейная обрезка совпадает с прежним измерением префиксов при ×1/1,25/1,5/2/3,
  для кириллицы, kerning, fallback и полужирного начертания. Метрики также по-прежнему
  сравниваются с fontdue в тестах предыдущего этапа.
- Объединённая панель сравнивается с двумя последовательными слоями прежнего pipeline,
  включая полупрозрачный источник и AA-края: максимум 3 уровня канала из 255 из-за
  округления двух композиций (отдельные примитивы по-прежнему ≤2).
- Готовая основа Control Center сравнивается с рисованием на месте в светлой/тёмной теме
  при ×1/1,25/2, с toast и без него. Изменение ползунка меняет кадр, инвалидация удаляет
  основу. Допуск сравнения — 2 уровня канала.

Воспроизведение после сохранения release «до»:

```sh
cargo build --release
dbus-run-session -- cargo test -- --include-ignored
# Сравнение времени кадра — без подробного трейсинга и readback:
python3 bench/raster-check.py --before /tmp/feather-ui-before \
  --memory-sample-ms 100 --width 1920 --height 1080 \
  --visual-ui --screenshot-ms 2000
# Разбор стадий — отдельно, с диагностическим выводом:
FEATHER_PROFILE_UI=1 python3 bench/raster-check.py --memory-sample-ms 100
```

Для активной сессии самого Пёрышка явно задать её `WAYLAND_DISPLAY` и убрать устаревший
`HYPRLAND_INSTANCE_SIGNATURE`; для Hyprland скрипт меняет размер только своего PID.
Снимки — отдельными запусками `FEATHER_DEBUG_OPEN=menu-app|cc` с
`FEATHER_DEBUG_SCREENSHOT`; readback не должен входить в профиль.

## Результат release

Сравнивался сохранённый release после оптимизации памяти шрифтов с текущим release.
Сборка без предупреждений; `dbus-run-session -- cargo test -- --include-ignored` —
22 passed. Ниже обычный FEATHER_PROFILE без FEATHER_PROFILE_UI и screenshot readback.
«Первый CPU-кадр» — прежний wall-таймер всей подготовки грязных CPU-буферов, не только
панели. Хост интерактивный, время заметно меняется между прогонами: это два конкретных
сравнения, не гарантия верхней границы.

| Метрика | Активный Feather, 2880×1800 ×2, до → после | Hyprland, 3840×2160 ×2, до → после |
|---|---:|---:|
| Меню приложения, первый CPU-кадр | 15,65 → 7,61 мс | 11,22 → 2,75 мс |
| Control Center, первый CPU-кадр | 18,81 → 6,42 мс | 28,82 → 3,40 мс |
| Spotlight, первый CPU-кадр | 6,92 → 6,85 мс | 13,24 → 11,17 мс |
| Launchpad, первый CPU-кадр | 1,94 → 0,90 мс | 3,01 → 1,15 мс |
| RssAnon после закрытия Launchpad | 33,79 → 41,79 МиБ | 30,55 → 35,70 МиБ |
| Наблюдаемый пик RssAnon, пробы 100 мс | 43,52 → 48,69 МиБ | 46,96 → 53,51 МиБ |
| Простой, тиков/5 с | 0 → 0 | 1 → 0 |

В обоих случаях активен tty3. Первый столбец — тестовое окно внутри работающего Feather
на wayland-2, анимации ~59–65/с. Второй — собственное окно на **неактивном** Hyprland
wayland-1, размер 1920×1080 logical, screenshot физически 3840×2160 в предыдущих
визуальных проверках. Там ~24–25/с из-за отсутствия активного vblank хоста; этот столбец
проверяет память/CPU при 4K, **не** приёмку FPS. Сессия пользователя не переключалась.

Цена готовой основы CC видна в памяти: в 4K после закрытия Launchpad +5,14 МиБ,
наблюдаемый пик +6,55 МиБ. Итоговый пик 54796 КиБ = 56,11 МБ, ниже 60 МБ, но пробы
не доказывают отсутствие более коротких пиков. Подготовка основы на worker заняла
~6 мс; главный поток её не ждёт. В простое worker спит, тиков в финальных прогонах 0.

Просмотрены menu-app, CC и стресс со сменой темы/масштаба. Отдельные запуски с readback
используют дополнительную память CPU/GPU для снимка и не входят в таблицу бюджета:
их кратковременные RssAnon 77–94 МБ нельзя выдавать за обычный рабочий профиль.
Геометрия/текст/стекло сохранены. Известное перекрытие CC уведомлением осталось;
Wi-Fi/звук пока заглушки, их реальные службы и иконки записаны следующим этапом.

**Приёмка всех бюджетов остаётся открытой:** на активном хосте первые кадры меню/CC
всё ещё >4 мс, Spotlight и восстановление окна также требуют работы. Пики сцена+GL
>1 мс сохранились. DRM/возврат VT/libinput lag проверяются отдельно пользователем;
работающий процесс на tty3 при проверке не перезапускался.

Артефакты этой проверки: `/tmp/feather-ui-check/backdrop/{before,after}.{log,json}`,
`/tmp/feather-ui-check/backdrop-4k/{before,after}.{log,json}`; снимки — в `backdrop/`.
Промежуточные активные 4K-прогоны до добавления основы CC давали меню 9,46→9,69 мс,
CC 26,52→6,96 мс: ускорение меню нестабильно, по одному удачному замеру 2,75 мс
считать задачу целиком принятой нельзя.
